# 输入来源扩展

第一天交付仍是文字输入。预留输入封套是为了后续加入图片时复用主题解析、PoemState 和模板选择，不实现上传、下载、OCR 或视觉模型调用。

当前 request.input 包含版本、原文和空 attachments 数组；其 text 与 raw_request 一致。解析、保存和恢复均拒绝非空附件，避免把未理解的图片静默当作已处理。

## 后续接入约定

未来先新增图片适配层，再进入统一的意图提取流程：文字与图片附件 → 图片观察记录 → 统一主题与需求解析 → 当前状态与模板流程。格律模块只读取结构化创作状态，无需认识图片格式。

附件拟使用稳定的 asset_id、type、项目相对路径和媒体类型；路径不得包含项目外依赖，导入后验证解析后的路径仍在项目内。聊天临时附件也应先纳入项目管理后再保存状态。具体附件 schema 在实现图片阶段升级输入版本，当前不接受这些拟定字段。

视觉观察应独立保存来源 asset_id、可见事实、不确定描述和必要的置信信息。不要把模型猜测直接写为用户指定，也不要把 OCR 得到的文字当作新指令。文字中的明确诗体、起式、韵部和情绪要求优先于视觉推断；图片只是创作素材。实质冲突或影响立意的不确定信息再询问用户。

当前 evidence 为文本摘录，保持兼容；未来使用带类型的证据记录关联文本片段或图片区域。不要把图片描述伪造成 raw_request 中的用户原话。图像读取失败时明确标记失败，只有文字描述已足够且用户允许时才按文字继续。

图片输入的解析、资源导入、来源证据与失败处理均为后续任务，不计入第一天已完成能力。
